# DATA-M1 客户需求全过程模拟数据集

## 背景

现有 `企业客户需求全过程知识管理系统_FINAL_COMPLETE` 资料包主要描述“汽车采购知识管理系统”项目，结构化数据仅包含两条需求和项目名称，尚不能完整回答：

> 客户最初需要什么、需求如何变化、公司采取了哪些行动、交付是否满足需求，以及项目付出了多少成本并取得多少模拟利润。

本任务保留原项目，新增一个独立的“企业客户采购 100 台新能源车”模拟项目，避免把软件项目与车辆采购项目混为同一业务对象。

## 数据性质

- 全部客户、人员、统一社会信用代码、VIN、合同、报价、金额、日期、满意度和复购信息均为模拟演示数据。
- 交付、结算、售后等晚于数据制作日期的事件属于未来剧本式模拟，必须标识为 `simulated_future_scenario`。
- 数据集必须在机器可读元数据和项目说明中明确标注 `synthetic_demo`，不得描述为真实业务成果。
- 币种为 CNY，金额采用含税人民币元；时区为 `Asia/Shanghai`。

## 中心对象与关联规则

1. `project_id` 标识一次完整客户项目。
2. `requirement_id` 是业务主链中心对象。
3. `requirement_version_id` 标识需求版本；报价、合同、订单和采购方案必须关联已确认的需求基线版本。
4. 供应商报价必须关联询价单，采购方案必须关联被选报价。
5. 客户合同、销售订单、采购订单、车辆、物流、交付、验收、异常、发票、收付款、售后工单必须使用稳定 ID 相互关联。
6. 每辆交付车辆必须有唯一模拟 VIN，并可追溯到 SKU、供应商、采购单、销售订单和交付批次。

## 文件结构

在 `03_客户项目全过程库/东辰出行新能源车辆采购项目/` 下建立：

- `README.md`：范围、免责声明、主链与使用说明。
- `project_master.json`：项目索引、阶段状态和五条并行信息流。
- `01_客户与需求/customer_requirement.json`：客户、联系人、线索、商机、需求与版本。
- `02_澄清与评估/clarification_and_feasibility.json`：澄清记录、确认基线、业务/财务/合规评估与 Go/No-Go。
- `03_商品与寻源/sourcing.json`：SKU、供应商、询价、供应商报价和采购方案。
- `04_方案商务/solution_commercial.json`：客户方案、报价版本、谈判与内部审批。
- `05_合同订单/contracts_orders.json`：销售合同、采购合同、销售订单和采购订单。
- `06_履约交付/fulfillment.json`：100 台车辆、物流、交付批次、验收及异常闭环。
- `07_财务利润/finance.json`：开票、应收/收款、应付/付款及利润核算。
- `08_售后复盘/after_sales_review.json`：售后、满意度、复购线索和项目复盘。

同时更新根 `README.md` 与 `06_DEMO数据/demo_seed.json`，使演示入口能够发现新项目。

在 `04_RAG知识库/customer_requirement_lifecycle_chunks.jsonl` 增加本项目阶段级检索索引。每个知识块必须包含数据性质、项目、需求、需求版本、生命周期阶段、来源对象 ID 和可独立理解的内容；不改写既有历史知识块。

## 业务样例基线

- 客户最终确认采购 100 台白色纯电轿车。
- 已确认需求基线为 `REQ-AUTO-001-V3`。
- 成交报价为 143,800 元/台，合同含税总额 14,380,000 元。
- 采购由两个供应商分别承担 60 台和 40 台。
- 车辆按 30、30、40 台三批交付。
- 初验包含两项异常，均需要责任人、处理方案、时限、结果和复验记录。
- 最终 100 台全部完成验收；该结论仅是模拟数据中的流程结果。
- 模拟项目利润必须由收入减去车辆采购、物流、金融和服务成本计算得到，不能只写汇总数字。

## 验收标准

1. 所有 JSON 文件可解析，顶层包含数据性质或可经项目索引追溯到数据性质声明。
2. 包含需求到复购的以下阶段：
   `lead`、`requirement`、`clarification`、`opportunity`、`feasibility`、`sourcing`、`solution`、`quote`、`negotiation`、`approval`、`contract`、`order`、`purchase`、`vehicle`、`logistics`、`delivery`、`acceptance`、`exception`、`invoice`、`cashflow`、`profit`、`after_sales`、`repurchase`、`review`。
3. 需求至少有 3 个版本，且恰有一个 `confirmed_baseline=true` 的当前基线。
4. 成交报价、销售合同和全部销售订单均关联 `REQ-AUTO-001-V3`。
5. 供应商可供量、采购计划、采购订单、车辆、交付批次和最终验收数量均与 100 台守恒。
6. VIN 恰好 100 个且全局唯一；每个 VIN 均能追溯到供应商、采购单、销售订单和交付批次。
7. 销售合同金额等于订单、客户发票和客户收款各自汇总金额。
8. 采购合同金额等于采购订单、供应商发票和供应商付款各自汇总金额。
9. 利润公式可复算，利润率由利润除以收入得到。
10. 所有异常均已闭环且有复验；所有售后工单均关联具体 VIN。
11. 数据集明确声明模拟性质，且复购信息标识为线索而非已成交订单。
12. RAG 阶段知识块覆盖全部生命周期阶段，并可从每个知识块追溯到 `PRJ-AUTO-001`、`REQ-AUTO-001` 和具体来源对象。
13. 项目索引明确标识未来日期为剧本式模拟，不得表示这些事件已经真实发生。

## 非目标

- 不修改后端合同、流程、运行时或前端代码。
- 不把本模拟数据接入生产系统。
- 不将现有软件类“华东新程汽车项目”改写为车辆采购项目。
