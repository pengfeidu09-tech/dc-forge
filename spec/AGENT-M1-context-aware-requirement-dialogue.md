# AGENT-M1 上下文感知需求对话

## 目标

飞书客户 Agent 必须把客户当前回答、历史问题、需求状态和场景 Skill 连成一条可持续的需求澄清链路。客户已经回答过的问题不得因为答案是“没有”“不清楚”或“暂未确定”而被原句重复追问。

## 范围

- 飞书客户需求提取与下一问题规划。
- 客户知识问答的对话上下文。
- 需求场景 Skill 的动态选择。
- 飞书事件的跨进程幂等认领。
- 不修改冻结的 contracts、process 和 runtime 模块。

## 功能要求

### 1. 否定与未知回答

当正在澄清审批规则时，以下回答均是有效信息：

- 没有规则、没什么规则、没有固定阈值；
- 暂时不清楚、暂未确定、不知道。

系统必须创建 `approval` 需求项，至少包含：

```json
{
  "category": "approval",
  "value": "当前没有明确的金额审批阈值",
  "parameters": {
    "rule_status": "not_defined",
    "needs_internal_confirmation": true
  }
}
```

“不清楚/不知道”使用 `rule_status=unknown`；两种状态都表示客户已回答且正式执行前待其内部采购、财务或制度负责人确认，不能被解释成已确认存在某个审批规则。

### 2. 原子化提取

客户回答“采购价格符合预期，后续服务完善”时，必须分别产生：

- `budget`：价格或预算预期；
- `deliverable`：交付、质保或售后服务要求。

这些信息不得写入 `ext:procurement:supplier_entry_policy`。证据摘录必须来自客户原文。

### 3. 问题历史

每次向客户提出的问题必须持久化以下信息：

- 项目、问题 ID、问题文本、目标类别；
- 提问时的需求状态版本；
- `asked / answered / dismissed` 状态；
- 回答对应的客户来源 ID。

新的客户需求回答应把上一个待回答问题标记为 `answered`。问题历史必须传给冻结的 `QuestionPlanner`，已问过的问题不得原句重复出现。进程重启后仍须保持该行为。

### 4. 动态 Skill

- 汽车制造企业的供应商准入、集团或多基地招采场景使用 `automotive-procurement-v1`。
- 高校、学校、事业单位、政府或公共机构采购使用 `procurement-core-v1`。
- 普通采购场景默认使用 `procurement-core-v1`。
- Skill 选择必须结合当前消息和已有需求状态；组织属性优先于“车辆/汽车”等采购标的词。

### 5. 不知道时继续推进

客户对审批规则表示没有、不清楚或未确定后，回复必须：

1. 明确复述已记录的审批状态；
2. 给出非法律结论的参考确认框架，包括内部采购/财务制度、适用采购限额与固定资产管理；
3. 说明该项已标记为待内部确认；
4. 继续询问下一项尚未回答的信息，例如总预算或交付时间。

不得再次要求客户立即给出同一个审批阈值。

### 6. 指代消解上下文

客户问“这个一般怎么做”时，客户知识 Agent 的请求必须包含：

- 最近的客户与 Agent 对话；
- 当前需求摘要；
- 当前待澄清问题及目标类别。

知识 Agent 应据此理解“这个”所指主题。上下文只用于规划和回答，不改变 MCP 的权限、项目和时间边界。

### 7. 跨进程事件去重

飞书 `event_id` 必须在共享 SQLite 中以唯一键原子认领。两个机器人实例连接同一数据库时，仅一个实例可以处理同一事件；进程内缓存可保留为快速路径，但不能作为唯一幂等保障。

## 验收标准

- 示例回答被拆成 approval、budget、deliverable 三类需求，且没有错误的供应商准入项。
- 审批缺口不再是 `missing`，原审批问题不会重复出现。
- 高校车辆采购选择核心采购 Skill，不触发汽车制造业的多基地、集团和 SRM 问卷。
- “这个怎么做”进入知识 Agent 时携带上一问题和需求摘要。
- 重启需求编排器后问题历史仍有效。
- 两个服务实例共享 SQLite 时，同一飞书事件只回复一次。
- 所有新增行为由自动化测试覆盖，契约测试继续通过。
